# Interview Prep Flashcards

A spaced-repetition flashcard app for CS fundamentals interview prep — OS, DBMS, OOP,
and system design basics. Built to be used daily, not just shipped.

Two halves, **both Java**:

- **Android client** — native XML views, offline-first, where the daily studying happens
- **Spring Boot backend** — stores cards and progress, runs SM-2 scheduling, serves the API

Java on both sides is a deliberate constraint rather than an accident: the point is to
demonstrate Java competency end to end. It costs something real on the client — Jetpack
Compose is a Kotlin compiler plugin, so the UI is XML views.

## What it does

Cards are scheduled by **SM-2**, reimplemented from the version proven out in
[DSA Tracker](https://github.com/VSDeadShot/DSA-Tracker) — that project covers coding
problems, this one covers conceptual knowledge. The port fixes a bug in the original:
DSA Tracker derives the next interval from the previous interval alone, so a lapse costs
one day and nothing else. This version tracks repetitions explicitly and resets them on a
lapse, so recovery runs 1 day → 6 days → ease-scaled. Two golden-vector tests exist
specifically to pin that difference.

Cards can also be **generated by Gemini** — the backend holds the key and calls the model
behind `POST /cards/generate`, so nothing model-related is ever exposed to a client. A
generated batch lands in a review band on the card list, and each candidate is added,
corrected first, or discarded. Nothing reaches the study queue unreviewed.

## The client works offline

Every screen reads a local Room cache; the network's job is to keep that cache current,
not to answer a question a screen asked. Studying, writing, editing and archiving all work
with the radio off.

- Reviews queue in an outbox and replay **per card**, so one card the server keeps
  refusing stalls only itself
- A review answered offline gets a locally predicted schedule immediately, replaced by the
  server's answer when it syncs — both run the same arithmetic on the same inputs
- Every request carries a client-generated idempotency key, so a lost response cannot
  apply SM-2 twice
- The streak is **never** computed locally: its rule needs the whole review history, and a
  confident zero shown to somebody thirty days into a run is the worst thing the app could do

## Authentication

Signing in with a passphrase exchanges it for a short-lived **bearer token**. There is no
API key: a static secret compiled into a client build is extractable by anyone holding the
build, cannot be withdrawn without shipping another, and identifies nobody.

- Passphrase hashed with **bcrypt**; tokens stored as a **SHA-256 digest** — different jobs,
  and the reasoning is written down in `docs/api-contract.md`
- Access tokens last an hour, refresh tokens thirty days, and **using a refresh token
  replaces it**
- Presenting a spent refresh token means two parties hold it, so the whole token family is
  revoked and both are sent back to the passphrase
- Sign-in is rate-limited per address over a rolling window, with a second global limit that
  cannot be evaded by varying a forwarded header

The app is optionally gated behind a fingerprint, face or device PIN. That gate is on the
interface only and is deliberately not bound to a Keystore key — an auth-bound key cannot be
used by the background sync, which by definition runs when nobody is present to authenticate.

## Deployment

The backend runs in a container on Render behind TLS, against managed PostgreSQL. Locally it
binds loopback only: one credential over plain HTTP has no business being offered to the
local network.

Release APKs are signed with an upload key held outside the repository, and shrunk with R8.
The keep rules are the load-bearing part — Moshi reads the DTOs reflectively, so their field
names *are* the JSON contract and no library's consumer rules protect them.

## Running it

Two independent Gradle builds; neither knows about the other.

```bash
cd backend && ./gradlew test    # full suite, no database setup needed
cd backend && ./gradlew bootRun # needs local PostgreSQL 17 + FLASHCARDS_DB_PASSWORD

cd android && ./gradlew build   # compile, unit tests, lint, both APKs
```

`android/local.properties` is gitignored and written by hand — see `CLAUDE.md`. Only
`sdk.dir` is required to build.

## Tests

**621 tests**, and the setup is the part worth mentioning. The backend suite starts a real
PostgreSQL 17 in-process rather than using an in-memory stand-in, because H2 would quietly
accept things real Postgres rejects and this schema leans on `timestamptz`, identity columns
and a partial index. Flyway migrates a blank database on every run, so each run also proves
the migrations still apply from nothing. `./gradlew test` needs no local database.

The Android database tests run real SQLite under Robolectric for the same reason, and the
remote tests run a real `MockWebServer` on a loopback port so they exercise OkHttp, Retrofit
and Moshi together rather than a stub standing in for them.

What a test suite cannot prove is checked by running the thing: the app has been driven on an
emulator against the deployed backend — sign-in, sync, token renewal, session expiry, an
offline review reaching the server on reconnect, and AI generation end to end from the sheet.
